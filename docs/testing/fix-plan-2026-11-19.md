# Fix plan from the 2026-11-19 code review

Source: a read-only review of the Go engine, frontend, native workers, GOOSE engine,
network service, installer and license server. Nothing was run on Windows. Items marked
**checked** were re-read in source by the coordinator; the others come from one reviewer's
reading and must be confirmed by the fixer before changing code.

Rules for whoever fixes these:

- One item = one small change with a test that fails before and passes after. No refactors,
  no new features, no redesign. If a fix needs a design change, stop and ask the owner.
- Follow `AGENTS.md`: under 300 lines per file, change record, ledger entry, `verify.py`.
- The Python backend is frozen; fix the Go engine only unless the owner says otherwise.
- Do not build the EXE.

## Part A: must fix before the next release

These can lose a customer's work, break their PC's network, operate a real device wrongly,
or crash or hang the app in normal use.

### A1. Drawing edit lost by a project refresh (checked)

- Where: `studio/frontend/src/state/useStudio.ts` `apply` (line 38) and `refresh` (line 44).
- Problem: a `GET /project` answer replaces the local project even when an edit is waiting
  in the 400 ms save timer. The timer then saves the old drawing and shows "All changes saved".
- Fix: while a save is pending or in flight, keep the local `diagram` when applying a refresh.
- Test: frontend unit test: edit, deliver a refresh before the timer fires, expect the PUT to
  carry the edited diagram.

### A2. Failed save throws the edit away (checked)

- Where: `useStudio.ts` lines 67-71.
- Problem: any PUT error calls `refresh()`, which puts the server's old drawing back. If the
  engine is down the refresh error also hides the real reason.
- Fix: keep the local drawing, show "Not saved" and try again on the next edit or on Save.
  Refresh only when the server answers with a revision conflict.
- Test: PUT fails with a network error; local diagram unchanged, state "Not saved".

### A3. Power cut can leave the project unreadable

- Where: `studio/engine/internal/store/autosave/snapshot.go:172-186`, `file.go:30`.
- Problem: the snapshot is written and renamed without `Sync`, and the journal is then
  trimmed because of it.
- Fix: fsync the temp file before the rename; trim the journal only after that.
- Test: unit test that the write path calls sync before rename (use the existing file seam).

### A4. A damaged journal stops the app from starting

- Where: `studio/engine/internal/app/wire_project.go:34-37`.
- Problem: any fold error aborts start-up; the customer gets a failure and must move files
  by hand.
- Fix: move the unreadable journal and autosave into the existing recovery folder, start with
  the last good project (or empty) and show one clear notice. Never delete the files.
- Test: start with a corrupt journal; the app composes and the files are in recovery.

### A5. Save can say OK when the write failed

- Where: `studio/engine/internal/store/autosave/snapshot.go:86-99` (`Flush`).
- Problem: returns nil when a later attempt finished, even if that attempt failed.
- Fix: return the last error whenever the attempt covering the target failed.
- Test: two overlapping flushes with a failing writer; both report the error.

### A6. The service removes addresses it did not add (checked)

- Where: `studio/engine/internal/labnet/handler_real.go:128-132`,
  `studio/engine/internal/labsetup/realcards.go:146-156`, `internal/netcfg/approval.go:60-63`.
- Problem: at Stop, launch and exit every "approved" address present on a real card is
  removed. If that address is now the PC's own, the PC loses its network.
- Fix: remove only addresses recorded in the journal as added by ScadaBench and still
  outstanding. Never remove an address from a DHCP card.
- Test: approved address present but not journaled as ours; no remove request is sent.

### A7. Gateway Stop does not cancel waiting commands (checked)

- Where: `studio/engine/internal/gateway/service/commands.go:29-45,61`, `stop.go:67`.
- Problem: queued SCADA commands keep running after Stop, each up to 30 s, and can operate a
  real breaker minutes later. When the queue is full a goroutine per command is started and
  order is lost.
- Fix: Stop empties the queue and answers each waiting command "refused: gateway stopped";
  `execute` refuses when the gateway is not running; a full queue refuses instead of spawning.
- Test: queue three commands behind a slow one, Stop; only the running one executes.

### A8. Real-device command timeout reported as failed; double operate

- Where: `studio/engine/internal/realcmd/service.go:54-58`, `internal/tools/control/client.go:84`,
  `internal/api/liveapi/operate_route.go:24`.
- Problem: after 30 s the app says "failed" but `studio_control` may still complete the
  operate. A retry or a double-click sends the command again.
- Fix: on timeout kill the control client and report "result unknown, check the position
  before trying again". Refuse a second operate for the same IED and reference while one is
  in flight.
- Test: slow fake client; timeout gives the "unknown" event and the process is gone; a second
  request during the first is refused.

### A9. One malformed frame crashes the GOOSE engine (checked)

- Where: `studio/goose_engine/internal/frame/goose.go:57-59` (`Parse`).
- Problem: a 26-byte VLAN-tagged frame with EtherType 0x88B8 reads past the end and panics;
  the frame goroutines have no `recover`, so all GOOSE stops for the Run.
- Fix: check the length before every read in `Parse`; add `recover` (log and continue) to the
  bus and uplink receive loops. Also guard `e.bus` in `fromBus` (`engine/engine.go:112`).
- Test: table test with the 26-byte frame and other truncated frames; add a Go fuzz target.

### A10. Stop or Quit hangs when a worker stops reading

- Where: `studio/engine/internal/native/request.go:42`, `internal/tools/worker/process.go:179`.
- Problem: the pipe write is outside the request timeout. `Close` writes "stop" first, so it
  blocks and never reaches the kill.
- Fix: put the write under the same deadline; on timeout kill the process.
- Test: fake worker that never reads stdin; `Close` returns within the timeout.

### A11. Gateway shows "running" with no process

- Where: `studio/engine/internal/gateway/service/stop.go:67-76`.
- Problem: when halt times out the process is closed but the state is never set to stopped.
- Fix: set stopped (or failed) on every exit path.
- Test: halt returns an error; state is not "running".

### A12. Modbus server can be locked out and leaks threads

- Where: `studio/native/gateway/modbus_server.cpp:122-131` (no receive timeout),
  `:115` with `:77-79` (threads only joined at stop).
- Problem: four idle connections block the real master for the whole Run; every reconnect
  leaves a finished thread behind.
- Fix: receive/idle timeout on client sockets; reap finished connection threads.
- Test: native test: open four idle sockets, wait past the timeout, a fifth can read.

### A13. Two Modbus points can share registers without warning

- Where: `studio/native/gateway/point_table.cpp:32-34`, `modbus_pdu.cpp:112-133`.
- Problem: uniqueness is checked per kind, but FC3/FC4 merge kinds and floats use two
  registers, so one point silently overwrites another.
- Fix: check register spans across kinds when the table loads and refuse with a message that
  names both points. Show the same message in the gateway page.
- Test: float at 10 plus float at 11 is refused.

### A14. Gateway stop waits 15 s per outstanding command

- Where: `studio/native/gateway/command_bridge.cpp:16-29`, `modbus_pdu.cpp:163-173`.
- Fix: a cancel that wakes all waiters before the threads are joined; the FC15 loop checks
  `running`.
- Test: stop during an outstanding command returns in under a second.

### A15. Blank window on any render error

- Where: `studio/frontend/src/main.tsx:24`.
- Problem: no React error boundary; an unexpected SCL shape gives a white page while IEDs
  keep running.
- Fix: one boundary with "Something went wrong. Your IEDs are still running." and Reload.
- Test: a child that throws renders the message.

### A16. Buttons re-enable while work is still running

- Where: `useStudio.ts:128-133` (`busy` is one boolean).
- Fix: count running tasks; busy while the count is above zero; keep the first error.
- Test: two overlapping `perform` calls; busy stays true until both end.

### A17. Real-IED connection form loses what you type

- Where: `studio/frontend/src/features/devices/DeviceConnection.tsx:19`.
- Problem: the effect depends on `ied.live`, a new object after every refresh.
- Fix: reset the draft only when the IED id or the saved values change.
- Test: re-render with an equal `live` object keeps the draft.

### A18. Real-IED values stay "fresh" after a read error

- Where: `studio/engine/internal/acquisition/session_run.go` (`live()`, near line 227).
- Fix: mark values stale on every exit from `live()`.
- Test: read error path marks stale.

### A19. Failed "add IED to a running station" leaves the IED running

- Where: `studio/engine/internal/runtime/run_selection.go:70-78`; also the unlocked writes in
  `supervisor.go:129` and `actor.go:42`.
- Fix: on any error after the worker started, stop and forget it; publish the worker under
  the lock only after start succeeds.
- Test: error after start; the worker is closed and not listed.

### A20. Worker says "IED already started" after a failed start

- Where: `studio/native/worker/server/server.cpp:88-99`.
- Fix: scope guard that calls `stop()` if anything throws after the server is created.

### A21. Lemon Squeezy: key issued without checking the amount (checked)

- Where: `license-server/internal/api/lemon.go:125-136`.
- Fix: accept only when the order subtotal and currency match the current price, the same
  rule PayPal uses (`paidAmountAccepted`). Log and ignore otherwise.
- Test: paid order with a lower subtotal issues no key.

### A22. Test or sandbox payments create real lifetime keys

- Where: `license-server/internal/api/lemon.go:116,130`, `deploy/lemon.ps1:7,59`.
- Fix: keys from test or sandbox orders are short trials, never lifetime.
- Test: test-mode order yields a trial certificate.

### A23. Refund that arrives before the order is ignored

- Where: `license-server/internal/api/lemon.go:143`, `checkout.go:171`.
- Fix: remember the refunded order id so a later `order_created` issues nothing.

## Part B: decided by the owner (2026-11-19)

Do these after Part A, same rules.

### B-1. Licence sharing: virtual machines yes, other PCs never

- What the finding means: a licensed PC can share its licence with the VMs running on it.
  The host decides "this is my virtual switch" partly from the network card's **name**
  (`hostkey/adapters.go:22`, the `^vethernet` match), and Windows lets anyone rename a card.
  So someone who wants to cheat can rename a normal LAN card "vEthernet", and other real PCs
  on that LAN can then get the licence. A normal customer never hits this; it is a loophole.
- Fix, host side: recognise a virtual switch from the adapter description only (the driver's
  text, which renaming does not change), never from the name alone.
- Fix, asking side: a computer uses a host's licence only when Windows reports that it runs
  inside a virtual machine (`vm_evaluate.go`; first check what the existing "this computer is
  a virtual machine" detection already covers).
- Tests: a physical adapter renamed "vEthernet (LAN)" is not served; a non-VM computer never
  asks a host; the existing real-VM evidence (`vm-host-real-vm-2026-10-22.md`) still passes.

### B-2. Server backup stays manual, but complete

- Keep the manual command; no schedule is added.
- Fix: `license-server/cmd/license-server/admin.go:157` also saves `sales.jsonl`,
  `admin-account.json` and `release.json`. Restore handles the same files.
- Test: backup then restore into an empty folder gives the same files.

### B-3. Uninstall offers to undo the firewall changes

- Where: `studio/packaging/installer.iss:72-91`.
- Fix: the uninstaller asks "Also remove the firewall rules ScadaBench added and switch
  Windows' own rules back on?" (ticked by default). When ticked it runs the app's journal
  clean-up with one administrator prompt, and reports a failure instead of ignoring it.
  Only journaled, app-owned items are touched.
- Test: the clean-up entry point with a journal of two rules and one disabled Block rule;
  the installer text is checked on the laptop.
